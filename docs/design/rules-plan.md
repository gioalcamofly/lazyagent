- **Status:** Accepted (2026-10-24; Q-R1-Q-R26 answered, all as recommended, notes on Q-R7 and Q-R24). Each phase gets an "As landed" note in §5 when it merges.
- **Proposal:** [0014-rules-catalog.md](../proposals/0014-rules-catalog.md). This plan does not repeat its rationale. It covers only what to build, where, and how to prove it. Open questions Q-R1-Q-R26 and their answers are in the proposal; the phases below follow them.

- **Byte-identical:** every golden fixture in `tests/protocol/fixtures/` and every existing engine test stays unchanged through R1-R5 unless a phase says otherwise. New output fields are opt-in (`status_list {fields}`).

## 4. Test strategy

- **Oracle (R1).** `tests/engine/rules/oracle.py` is today's `derive()` verbatim. `test_oracle.py` runs every golden derivation case and 10 000 `Facts` from a seeded generator (agents' statuses, PR states, reviews, mergeable, checks, gestures, claims, holds, delegations, trackers, reports, queue items, ages) through both and asserts equal `Derived`. Kept until R2 removes the old code from the engine; the oracle file itself stays as a regression test of the built-in catalog.
- **Byte-identical.** No fixture under `tests/protocol/fixtures/` changes in R1, R3 (no `[*.qa]`), R4 (nothing configured) or R5 (no attestations). R2 adds fixtures for new methods only; the built-in merge becoming an item (Q-R22) is the one intended change, with its fixtures regenerated in R2 and called out in the PR.
- **Language.** Precedence, Kleene tables, unknown never matching, type errors with suggestions, size and depth caps, RE2 subset checks.
- **No network.** Actions artifacts and logs from fixtures through the existing fake `gh`.

## 5. As landed

### R1 as landed

Branch `rules-r1-catalog-evaluator`. A pure refactor: no fixture, no existing test and no output changed; no user rules, no new method, MCP tool, event or desktop change.

- **Modules.** `engine/rules/lang.py` (tokenizer, recursive-descent parser with the precedence of the proposal, type check, compile to closures, Kleene evaluator), `engine/rules/facts.py` (the registry), `engine/rules/catalog.py` (`[[rule]]` and `[[kind]]` loader, `Catalog.derive`, `kinds_of`), `engine/rules/__init__.py` (`builtin()`, compiled once), `engine/rules/builtin.toml` (package data: hatch ships every file under `src/lazyagent`, and `test_lang.py` builds the wheel and reads the file back from it). `concepts.toml`, `doc.py` and `preview.py` come with R6/R7.
- **Grammar.** As Q-R1: literals (text, numbers, durations `90s` `10m` `24h` `7d` in seconds, `true`/`false`, literal lists), `== != < <= > >=`, `in`, `not in`, `subset`, `known()`, `unknown()`, `empty()`, `not`/`and`/`or`, parentheses, `#` comments. Two additions the built-in table needed: `+` joins text (a number is written as digits), and the choice `c ? a : b` (text only; it takes `a` only when `c` is true, so unknown picks `b`, like a rule that does not match). Comparisons do not chain. A mixed `and`/`or` without parentheses compiles with a warning (none in the built-ins). Caps: 2000 characters, depth 32, 256 nodes. Type errors name the fact or value and suggest the closest (`pr.review is never 'aproved'; did you mean 'approved'?`).
- **Unknown.** A comparison, a `+`, or a function of an unknown is unknown, except `with()` (an unknown detail reads as empty) and `known()`/`unknown()`. A rule matches only on `true`. An output that comes out unknown reads as empty text, no level, `false`, or ball `stalled` (never reached by the built-ins: the oracle would show it).
- **Facts.** 59 facts, two scopes: `row` (from `status.Facts`, for row rules) and `item` (an actionables `Place` and, for the agent kinds, one agent). Each has a type, lower-case values for enums, a phrase (a noun phrase for now: the generated sentences are R6's), source, freshness and cost; all R1 facts are `free` or `poll`. Facts are memoised per row per pass. Facts the later phases bring (`tracker.qa`, `ci.failing_tests`, `ci.unrelated`, `decisions.*`, `presence` …) are not registered yet: they join with their phases. Additions to the proposal's list that today's table reads: `agents.idle`, `agents.first_running`, `config.stalled_after`, `queue.enabled`, `hold.note`, `delegation.agent`/`.fact`, `gesture.how`/`.waiting`/`.source`, and in the item scope `agent.status`/`.detail`/`.id`, `place.is_orchestrator`, `ci.pr_red`. `ci.first_failing` is the PR's first failing check on rows (as before) and the red Actions run's title, else that check, on inbox items (as before).
- **Functions.** `with`, `clip`, `park_text`, `waiting_text`, and `agents.detail_of("<status>")` (a literal status, checked against the enum). `ci.failing_tests_of` is R4's.
- **`then`.** `ball`, `level`, `state`, `blocks_agent`, `suggestion`, each also as `<field>_expr` (the proposal's `state_expr`, generalised: the queue rule takes its level from `items.top.level`, the label its ball from `gesture.ball`); `inherit = ["ball"]` (park) or `["state"]` (label) takes the field from the first matching rule below. **No default level in R1**: a rule without `level` has none, as today's label and reported-ball rows (the proposal's "default round" applies to user rules, R2). `verb`, `action` and `item` are not in R1's catalog (R2/R6).
- **Rules.** 35 rules for the 16 numbers, in today's order, ids from the proposal where it names them (`closed.merged`, `queue`, `merge`, `park`, `label`, …). Where one old branch had two numbers it is two rules (`reported_others` 10 / `reported_ball` 12; `tracker_you` 3 / `tracker_others` 10 / `tracker_ball` 12). `locked = true` marks the prefix (`closed.*`, `park`, `queue`, `claim`, `hold`, `held`, `delegated`); it has no effect until R2. The "no queue" branches are rules guarded by `not queue.enabled`; `items.*` are unknown without a queue.
- **Kinds.** The 14 kinds in their old order with level, title, rank and `blocks_agent`; `actionables.KINDS` is built from them (claims.py still registers `delegation` in code, after them). A `detector` names the code that finds candidates: `agents`, `pr` and `actions` kinds carry the condition and the state text and are evaluated per agent / per place; `exits`, `jobs`, `tracker`, `report`, `decision` stay fed by events or their stores (exits and jobs take their state text from the catalog). Ids, labels, details and runs stay in code.
- **`derive()`** in `engine/status.py` is one call into the catalog; `_derive_tail` and `_NEEDS_YOU` are gone from the engine. `Facts`, `Derived`, `fingerprint` and the row are unchanged.
- **Oracle.** `tests/engine/rules/oracle.py` is the old `derive`/`_derive_tail` verbatim (with copies of the constants they read). `test_oracle.py`: every case of `test_status.DERIVATION` (at two ages), 10 000 `Facts` from a seeded generator (agents, PR states incl. odd ones, checks, reviews, mergeable, reviewer counts, queue items, claims, holds, holders, delegations, trackers, reports, gestures with every park end, merged-into, activity, ages, stalled thresholds; the test also asserts that the samples reach every one of the 35 rules), and a run of `tests/engine`, `tests/protocol`, `tests/contract`, `tests/test_mcp_status.py` and `tests/test_status_cli.py` in a subprocess with `oracle_plugin.py`, which checks every `status.derive` call those suites make against the oracle (about 1 600 calls per run, the count moves a little with the projection's coalescing; no mismatch). A deliberate one-word change to a built-in state fails it.
- **Benchmark.** `test_bench.py`: 100 fixed seeded rows, 3 warm-up passes, the **median of 31 passes**, budget 2 ms × a factor (1 locally, 5 when `CI` is set, or `LAZYAGENT_BENCH_FACTOR`). GC off while timing; up to 5 rounds, the first under budget passes (noise only adds time, so a busy runner gets more chances and a real regression fails all five). Measured locally, quiet machine: catalog 0.5-0.8 ms, old `derive` 0.2-0.33 ms (about 2.5× slower, well inside the budget); with the whole suite and `cargo test` running beside it, 1.0-1.7 ms.
- **Tests.** `uv run pytest`: 2433 passed, 34 skipped (102 new: `test_lang.py` 60, `test_oracle.py` 41, `test_bench.py` 1). Desktop `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` (213 passed) unchanged and green; no file under `tests/protocol/fixtures/` changed.

### R2 as landed

Branch `rules-r2-user-rules`. User rule files, `--why`, and the one intended visible change: the built-in Merge is an inbox item (Q-R22).

- **Modules.** `engine/rules/user.py` (parse a file with the lines of each `[[rule]]` and its keys; compile one user rule over the definition it replaces; compose with the built-ins), `engine/rules/hub.py` (`RulesHub`: the two files, content hashes, the repo allow store, last good copies, `rules.changed` / `rules.errors`), `engine/rules/export.py` (`rules_catalog`'s payload, `lazyagent rules doc` Markdown, the `--why` and `rules show` text). `engine.rules` is the engine's hub; the status projection derives with `engine.rules.catalog`, re-checked on its tick (stat of the two files and the allow store; a changed file applies on that pass).
- **Files.** Global `$XDG_CONFIG_HOME/lazyagent/rules.toml`; repo `<repo root>/.lazyagent/rules.toml` (the engine's repo root, the main checkout). Top level: `version = 1`, `[[rule]]`; `[ci]` and `[ci_unrelated]` are accepted with a warning (read from R4/R5); any other key is an error, the rules still load. Caps: 256 KB (the file is ignored), 200 rules (the rest skipped), and the language's 2000 characters, depth 32, 256 nodes per expression.
- **User rule keys.** `id`, `says`, `when` or `and_when`, `then`, `before` or `after`, `disabled`. `then` adds `verb` (a verb from the list, or one word ≤ 12 characters), `action` (from the actions list, with a suggestion), `item`. `locked` and `num` are the built-ins' own. A rule with ball `you` defaults to level `round` and to `item = true`; its state is clipped to 5 words. `and_when` narrows the definition it replaces and keeps the outputs it does not give (verb, action, item, inherit included). A replacement keeps the replaced rule's `num`; a new user rule has `rule: 0`.
- **Order.** Locked prefix (the built-ins marked `locked`, R1's) → repo new rules → global new rules → built-ins; a same-id rule replaces in place (repo over global over built-in); placements apply after, global first then repo. Errors, each skipping its rule alone with `fallback` saying what is in force: an override, `and_when`, `disabled` or placement against a locked rule; a placement to an unknown id or itself; both `before` and `after`; a cycle of placements (kept in file order); `and_when` with nothing to narrow; an unknown fact, value, function, verb or action; an item rule reading `items.*`, `queue.*`, `claim.*`, `hold.*`, `holder`, `delegation.*` (the queue's pass sees them only after it). A placement whose target was skipped is a warning (placed first). Expression errors carry the line of the term (the key's line plus the newlines before the error's position).
- **Last good and allow.** A file that parses is copied to `state_dir()/rules/global.toml` or `repo-<repo digest>.toml`; one that does not parse uses the copy (memory, then disk, so across restarts) and its error says `the last good version is in force`. The repo file applies only while its sha256 equals the one in `state_dir()/rules/allowed.json` (by repo root); otherwise the copy of the last allowed version applies (`applied: last_allowed`) or nothing, with an error naming the hash to allow. `rules_allow {hash}` takes the full hash or ≥ 12 characters, refuses a hash that is not the file's current one, and is the user's only.
- **Merge as an item (Q-R22).** Built-in `merge` has `item = true`, verb `Merge`, action `open_pr`. An item rule's row rule is gated: with the queue on it never matches a row. The projection's pass is now two loops: the facts the queue does not decide (gesture, report, activity …), then the item rules (per row, the first match below the locked prefix with the gates off, so a rule placed before `merge` keeps it away), then the queue's flush, then claims, holds, delegations and the rows. The item is kind `rule` (registered in code, level round, title the verb), id `Rule:<rule id>:<work item>`, with `rule_id` and `verb` (only these items carry the two keys). Dismissed or parked, the row reads `approved_ready` (new built-in, rule 12, stalled, `approved, CI green`) or whatever matches below. `actionables_list/get/mark` run the projection's first pass when it has not run yet. A parked work item that is ready to merge keeps the ball of the rules below Merge.
- **Fixtures changed (deliberate, the Merge item):** `status_list__rows`, `status_list__include_done`, `status_gesture__close` (the docs-index row: rule 4 → 2, `needs_you` set), `actionables_list__now_and_round`, `actionables_list__include_hidden`, `actionables_list__ci_failed_without_a_pr` (the Merge item, `round` count + 1). ### R3c as landed

Branch `rules-r3c-clean-base-merges`. R3b counted every merge of the base branch in `pr.commits_after_ready`, so each "Update branch" brought back a "new commits since your approval" Review that had nothing to review. A clean merge of the base no longer counts.

- **Rule** (`engine/base_merges.py`). A commit after the ready point is a clean base merge when it has exactly two parents, one an ancestor of `origin/<base>` or `<base>` (the PR's base branch), and its tree equals the automatic merge of the parents. A conflict resolved by hand or an extra edit changes the tree; a merge of another branch has no parent on the base; an octopus merge and every normal commit are not merges of two parents: all of these count.
- **The automatic merge**, local git only, never a working tree. git ≥ 2.38: `git merge-tree --write-tree --no-messages <p1> <p2>` (merge-ort: renames and several merge bases handled). Older git (the owner's machine runs 2.34): a temporary index (`GIT_INDEX_FILE`), `git read-tree -i -m --aggressive <merge base> <p1> <p2>`, each path still unmerged merged with `git merge-file -p` on its three blobs (`git cat-file` to temp files; a mode changed on one side takes that side's), `git hash-object -w --no-filters` and `git update-index --index-info`, then `git write-tree`. Not clean: a content conflict, a path deleted on one side and changed on the other, one added on both sides with different content. Undecidable, so counted: several merge bases (merge-ort would build a virtual one), a binary file, a symlink or submodule changed on both sides, a mode changed on both sides, a failing git step. read-tree has no rename detection: a rename on one side with an edit on the other reads as a conflict and counts; it can never make a merge look clean wrongly, since the result must still equal the commit's tree. Both paths write into a temporary object directory with the repo's own as an alternate (`GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`): the repository, its index and its refs are never written. The version is read once (`git --version`); tests force it.
- **Missing commits.** A merge GitHub made is not local. When the commit is not here, or no parent is on the local base, one `git fetch --quiet --no-tags --no-write-fetch-head origin <sha> refs/heads/<base>` (git ≥ 2.29; it also moves `origin/<base>` through the configured refspec, as `fetch_branch` already does; no `FETCH_HEAD`, no other ref, `GIT_TERMINAL_PROMPT=0`, 30 s timeout), at most once per commit every 10 minutes. Still missing, or a failed fetch: counted.
- **Force pushes.** The timeline's `HeadRefForcePushedEvent` gains `beforeCommit { oid } afterCommit { oid }`. A force push does not count when every commit gained (`rev-list after --not before origin/<base> <base>`) and every commit dropped (the other way) is a clean base merge, as when a base merge is redone on a newer base; at most 200 commits, else counted. A rebase or an amend counts. The merges it added are classified as commits of their own.
- **The head check.** `WorktreeService._ready_head` applies the same test to the commits between the head first seen after the ready event and the new one: moved only by clean base merges, no bump to 1 (and `base_merges_after_ready` reads at least that many). It now runs in the poll's thread with the classification (`_after_ready`, after the batch), under a lock shared with `_prune`.
- **Timeline and cost.** `PullRequestCommit` gains `commit { oid parents { totalCount } }`: measured, the second query stays 1 rate-limit point (20 PR aliases, cli/cli) and 1.3-1.5 s; no extra GitHub call. `PrInfo` gains `after_ready_merges`, `after_ready_pushes` (what the timeline counted) and `base_merges_after_ready`; the engine subtracts the clean ones from `commits_after_ready` (`BaseMerges.adjust`). Local cost, measured on this repository's last 27 merges of `origin/develop` on git 2.34 (the temporary index): 16 clean, 11 counted (9 conflicts resolved by hand, 1 delete/modify, 1 with two merge bases; each one also conflicts in git's own `merge-tree`), median 70 ms and at most 205 ms per merge, about 16 git calls; cached per (commit, base) after that (30 cached look-ups: 0.05 ms). A verdict that needs a fetch is kept only until the next fetch may run.
- **Unknown stays unknown.** No timeline: both facts unknown. A draft: 0 and 0. A merge that cannot be checked counts, so the row reads "new commits", never fewer than R3b would.
- **Fact** `pr.base_merges_after_ready` (num, row, cost `extra`, in `REVIEW_FACTS` so it turns the second query on): the clean base merges taken out. The README's fact table shows a state text using it.
- **Wire.** `pr_info` in `events.json` gains `after_ready_merges`, `after_ready_pushes`, `base_merges_after_ready`; the remote backend reads them back as tuples. Fixtures changed: `rules_catalog__builtin` only (the new fact and the new phrase of `pr.commits_after_ready`); the generated "How lazyagent works" page and the desktop's catalog copy with them.
- **Tests.** `tests/engine/test_base_merges.py` (25, 5 skipped on git < 2.38: the merge-tree half of the parametrized ones): temporary repos with an `origin` bare repo: a clean merge of the base (not counted), a conflict resolved by hand, a merge with an extra edit, a merge of another branch, a normal commit (counted), the local base branch, a mode change on one side (clean), a binary conflict and a criss-cross (undecided, counted), the repo never written, a merge pushed from another clone (as "Update branch") fetched once then clean, a failed fetch and its back-off, git < 2.29 never fetching, the version picking the path, bad input never reaching git, a redone base merge in a force push (not counted) against an amend and a rebase (counted), the head check, the timeline through a fake `gh` end to end, the cost cached.

### R4b as landed

Branch `rules-r4b-ci-readers`. R4's readers on a large monorepo CI: three blockers found by checking real runs, read-only. Nothing changes until a rule file gives a check `tests_from`.

- **B1, `^[` for ESC.** `gh` writes the two characters `^[` instead of the ESC byte when its output is piped, so a coloured log (pytest `--color=yes`, vitest in CI) had "no totals line". `actions._ANSI` now strips CSI, OSC (ended by BEL / `^G` or ST) and charset selection in either form; `_clean` is the one place logs are cleaned, so I7's failed-log summary and every parser get it. Fixtures: a coloured pytest log and a vitest log in the caret form, end to end.
- **B2, aggregate jobs.** `[ci.check."<job>"] aggregate = true | false` (no `tests_from` with it; a config with only aggregates configures nothing). An aggregate job is unrelated when every other failing job of its run that is not an aggregate is unrelated; else related, naming the first that is not (`waits on unit-tests (3.12), related: …`); with no other failing job (they were cancelled or skipped), related. `CheckResult.aggregate_of` (and `rules_explain`'s `aggregate_of`) lists them; its tests and base tests are empty (known), its point the deps' when they share one, its `base_fixed` theirs. **No workflow parsing:** GitHub's jobs list has no `needs`, and reading the workflow file at the run's sha costs a call and a YAML parser. The run's other failing jobs stand in for the needed ones: stricter (an aggregate never waits on a job outside its run, and a failing job it does not wait on is itself a failing check, so `ci.unrelated` is the same either way). **Detection is opt-in:** with `aggregate` unset a job is not an aggregate, since a misdetected lint or post-test job would be called unrelated and could unblock Merge on a real failure (a wrong "related" costs noise, a wrong "unrelated" a bad merge). `[ci_unrelated] detect_aggregates = true` (repo over global; `rules_catalog`'s `ci.detect_aggregates` only when on) turns on the heuristic: no `tests_from`, at least one other failing job, started at or after every other failing job's `completed_at`, and one or two steps of its own (GitHub's "Set up job", "Complete job" and "Post …" aside). `WorkflowJob` gains `started_at`, `completed_at`, `own_steps` from the jobs call it already makes.
- **B3a, JUnit artifacts of thousands of files.** The artifact's zip is streamed (`gh api repos/{owner}/{repo}/actions/artifacts/<id>/zip`, at most 20 MB, written to a temporary file; `gh run download` extracted everything to disk) and read one member at a time: a file without `<failure` / `<error` is only scanned for its `<testsuites>` / `<testsuite>` start tags' `tests`, `failures` and `errors` (a regex, no parse; the root `<testsuites>`'s own counts when it has them, else its suites' summed), the others are parsed. **Count check:** the `<failure>` and `<error>` elements found must equal the files' `failures + errors` when every file has them (`found 1 of 2 failures and errors its 5812 files count (58120 tests)`), else, as before, no check. GitHub's job-log endpoint redirects to blob storage and `gh` has no ranged download, so a ranged request was not used. `total` is still every line, so I7's "last 30 of N lines" is unchanged. **When the middle was dropped** only `pytest`, `jest` and `vitest` are trusted (one totals line at the end, the count check still applies; jest forgets its `FAIL` file at the cut); `go`, `cargo`, `junit-console` and `regex` add totals up over the log or print none, so they say `the log's middle (N lines) was not read`. The old 5 MB head cut in `parse_log` is gone.

### R4c as landed

Branch `rules-r4c-nongating-checks`. A noise review of a busy repo found most inbox items were not the owner's to act on; R4c takes out five kinds of them, and (asked during the phase) lets a base merge whose conflicts were only in generated files count as clean.

- **Non-gating and policy checks** (`engine/ci_tests.py`). `[ci.check."<name>"] gating = false` and `policy = true` (same name matching as `tests_from`; `gating = true` beside `policy` is an error; a table with only these keys configures mechanism A, so `CiConfig.configured` is true). `CiTests.gates` keeps the non-default gate of each failing check (an Actions check id, or a non-Actions check's lower-case name), and `CiTests.gate(c)` the effective one: a non-gating check whose failing tests are known to be the branch's (`known_related`: they pass at the base point) gates again; with unknown test data it stays non-gating (the trade-off the user accepts by setting it). Facts: `ci.gating_failures` (`ci.related_failures` minus non-gating and policy; without a `[ci.check]` table, equal to it), `ci.policy_failures`, `ci.first_policy`, `ci.only_nongating` (red, no gating failure, at least one non-gating or policy one; unrelated ones allowed). `ci`, `ci_failed` and `ci_red_no_agent` read `ci.gating_failures`; `ci.first_related` names a gating check first. The row's `ci_note` reads `eval-suite red · not gating` / `label-check red · policy`. A non-gating red has no item, so it is never auto-delegated.
- **"The merge is next"** for a policy check: the PR is open, `pr.human_approvals >= 1` (not `pr.review == "approved"`, which an app's approval sets; `[review] not_human` applies), `pr.mergeable == "mergeable"` and `empty(ci.gating_failures)`. `pr.human_approvals` gains an item getter (`Place.not_human` carries the rule files' list), and `Catalog.reads_review` is true when a `[ci.check]` has `policy = true` (the kind reads a review fact), so the review query costs nothing otherwise. Facts only (not the row's user-rule verb: the kinds are evaluated beside the rows, not after them, and a user's Merge rule may ask for more, which would hide a label that blocks the merge). New kind `ci_policy` (detector `pr`, Round, verb Fix, action `open_pr`, state `Fix label-check`, detail `policy check red: label-check; the rest is ready to merge`); the desktop's `kind_verb` knows it. The README's two Merge recipes read `(ci.state in ["green", "none"] or ci.unrelated or ci.only_nongating)`.
- **Parking a work item parks its items.** `ActionableQueue.flush` hides every item whose work item has a park gesture (until a past time hides nothing; an event's park is dropped by the projection's pass as before), except `now` items; `actionables_list {include_hidden}` lists them with the work item's park. Engine briefs (deep) of a parked row no longer reach To sit down with. The built-in `park` rule yields to a `now` item (`not (known(items.top.level) and items.top.level == "now")`: total with the queue off): an agent blocked on an approval takes the row out of Parked until answered. `counts.parked_needs_you` is kept for older clients and now stays 0.
- **The latest-created run wins.** `actions.verdict` already took the newest-created run per workflow (a re-run keeps its run's `created_at`). The PR's checks did not: the rollup lists every run's check runs, so a re-run of an old label-triggered run (replaying its old labels) kept a red beside a newer green run and `ci.state` read red. `worktree_manager._latest_runs` keeps, per (workflow name, job name), the check of the highest run id (run ids grow with creation); the GraphQL query asks `checkSuite { workflowRun { workflow { name } } }` (objects, no rate-limit points), `gh pr view` already gives `workflowName`. A check with no workflow name or run id (a commit status, another app) is kept as is.
- **Hang detection.** `[inbox] hang_seconds` (repo `.lazyagent.toml`, at least 60), else the same key in the global `config.toml` (an invalid value there warns and is ignored), else `LAZYAGENT_HANG_SECONDS` (the engine's environment: every repo), else 600; `Engine.hang_seconds`, passed to `AgentSession.check_hang`. On Linux, `session.tree_cpu_ticks` sums `utime + stime + cutime + cstime` of the agent's process tree from `/proc/*/stat`; each hang check (once a minute, only for running agents) samples it, and an agent whose tree used CPU since the previous sample (at most 90 s ago) is not hanged. Elsewhere, or with no previous sample, quiet alone decides. Item (a) of the brief (no hanged item while the agent's `ball = "agent"` report holds) is I4i's "agent holds the ball" folding, not repeated here.
- **mergeable UNKNOWN.** `WorktreeService._keep_mergeable`: a PR read with `mergeable` UNKNOWN (or empty) keeps the last known value of the same PR for `MERGEABLE_KEEP` (600 s) after it was last read; then UNKNOWN shows.
- **Generated files in base merges** (`engine/base_merges.py`). `[review] generated_paths` (globs: `**/` any directories, `*` and `?` within one, matched from the repo root; global and repo files, merged). A merge of the base whose tree differs from the automatic merge only in matching paths is clean, with the reason `base merge, only generated files differ`. merge-tree (≥ 2.38) runs with `-z --name-only` when paths are set and lists the conflicted paths; the temporary-index path merges every path it can, drops a matching one it cannot from the index (`mode 0`) and counts it as differing; a non-matching one ends it early as before. The commit's tree is compared with the automatic merge's by `git diff-tree -r --no-renames --name-only`. Verdicts are cached per path set. `pr.base_merges_after_ready` keeps its meaning (these included); `PrInfo.generated_merges_after_ready` and `BaseMerges.commits_since`'s third value count them, and the owner approval's Why? line says `(2 clean merges of the base not counted; 1 of them: base merge, only generated files differ)`. `rules_catalog.review.generated_paths`.
- **Not done.** `compare_to = "latest_base_run"` per check (a nightly as the base for suites with no push run at the build base): left out, a doubt for a later phase.
- **Tests.** `tests/engine/test_r4c.py`: the keys and their errors; a non-gating red (no Fix CI, the chip); a non-gating check with a new failing test (Fix CI back) and with unknown data (stays out); a gating check named before a non-gating one; a policy check before and once the merge is next, and beside a gating red; the README recipe's Merge; a parked work item hiding its items, an approval breaking through and the row back in Parked after; an engine brief of a parked row; `verdict` with a re-run of an older run; the PR checks' dedup in both shapes; `hang_seconds` from the file and the environment; `tree_cpu_ticks` on a fake `/proc`; a quiet agent using CPU; mergeable UNKNOWN kept, a new PR, the expiry. `tests/engine/test_base_merges.py`: a generated-only conflict clean on both git paths (and re-classified when the paths change), with another edit counted, a conflict outside the paths ending early, an edit of a generated file in a clean merge, the globs, merge-tree's output in both terminations. `test_owner_approvals` reads `commits_since`'s third value.


### R5a as landed

Branch `rules-r5a-required-checks-infra-rerun`. Two jobs the user did by hand: keeping the gating list in line with branch protection, and re-running jobs whose runner was lost.

- **Required checks** (`engine/required_checks.py`). `RequiredChecks` beside the Actions hub, every call through `ActionsHub._api` (its per-minute cap, back-off and `GithubHealth`). Per base: `branches/<base>` (`protection.required_status_checks.contexts` and `checks[].context`; readable with read access, unlike `.../protection`) and `rules/branches/<base>` (rules of type `required_status_checks`; when GitHub refuses it, the protection alone). A readable base with no required checks borrows the default branch's set (`repos/{owner}/{repo}` `default_branch`): source `default_branch`. Cached per branch for 6 h (a stale set stays until a new read answers); a 4xx is cached as unreadable for the same time (`HttpError` from `_api`), a call with no answer is not cached. Read only for the bases of red PRs (`StatusProjection._poll_actions` passes them to `poll(bases=)`), at most 2 bases a poll. `[ci] gating_from_protection = false` clears it and makes no call.
- **Gating** (`CiTestsHub._gated`). Precedence: a `[ci.check]` table that sets `gating` (now kept when `true`: `CheckConfig.gating_set`) or `policy` wins (`CiConfig.own_gate`); else, with the base's set known and every required check reported passed on the PR's head (`SUCCESS`, `NEUTRAL`, `SKIPPED`; a missing or running one is not), a red check not covered (`Required.covers`: job name, `<workflow> / <job>`, check id or status context, case-insensitive) is `nongating`; else as before. A known set makes `CiTestsHub.active` true (a verdict per row) though nothing is configured; with no set and no config the rows are exactly as before (`ci_tests` None). `CiTests.required` and `required_source` (`protection`, `default_branch`, `config`, `none`); facts `ci.required_source` and `ci.required_checks`; `rules_explain.ci_required` and, while red, a sentence appended to the answer (Why?).
- **Infrastructure re-runs** (`engine/infra_rerun.py`), the one CI write the engine makes alone, documented as a deliberate exception and switchable (`[ci] rerun_infra`, `rerun_infra_max_attempts`). The jobs read (`attempts/<n>/jobs`, already fetched once per red run attempt) are also parsed into `InfraJob`s (id, conclusion, first failing step, concluded steps), cancelled ones included. A run is a candidate when it concluded `failure` (a run cancelled on purpose, by a person or `concurrency: cancel-in-progress`, concludes `cancelled`: never; "The operation was canceled" is not a marker), is on the head (the verdict's fresh red runs: an older head's runs are ignored), and none of its non-passing jobs has a failing step or timed out; each job then needs a reason: one of `MARKERS` in its annotations (`check-runs/<id>/annotations`, read only for such a job, 3 a poll) or no step concluded. Skipped: nondeterministic checks, names with `eval`, policy checks, a run at the attempt cap; each (run, attempt, job) is tried once, one job per run attempt. After `gh run rerun --job <id>`, `InfraReruns.pending` makes the run read as queued (`ActionsHub.all_runs`) and its failed check queued on the PR (`Engine.get_pr_info` → `queued_checks`) until GitHub shows the new attempt, at most 15 min: the row's CI is running, so no item and no auto-delegation. The timeline gets a `ci` entry by `engine`; the log, INFO.
- **Outages.** `ActionsHub.poll` returns before any call while `GithubHealth` is not due (the projection already checked; now the hub does too); re-runs wait for `health.available`.
- **Tests.** `tests/engine/test_r5a.py`: the set from protection, rulesets (alone and added), the default-branch fallback, the 6 h cache, unreadable protection cached, no answer not cached, name matching, "every required check passed"; the keys; on the rows: a non-required red with the required green (no Fix CI, the chip, Why?), a required red, a required check still running, unreadable protection (as before), a project branch, config precedence both ways, protection off (`config`, no calls), the facts, an outage (no call); the markers, no step concluded, a failing step and a timeout, `parse_infra`; a re-run once per attempt up to the cap with the run queued meanwhile, a failing step, a run with a real failure beside (fail-fast), evals (by name, by workflow, nondeterministic) and policy checks, `rerun_infra = false` and the cap, a failed `gh run rerun` not retried, an outage, and on the row (running, no item, the timeline entry).
